## Executive summary

Tapboard's observed pour behavior has four interacting causes:

1. **Cross-tap sensor movement:** Operating Tap 2 produces a large transient drop on Tap 1's fast scale sensor. This is real input data, not just a UI card-selection bug.
2. **Over-sensitive start detection:** One sample dropping by 0.3 oz starts a pour, so physical coupling and ordinary scale impulses can trigger false sessions.
3. **Broken completion timing:** Every 0.2-second update restarts the settle timer, including flat and rising readings. A pour normally ends only when telemetry happens to pause.
4. **SSE overload:** Every HA state change serializes all HA entities and sends them to every browser. This produces a large backlog and can delay visible pour events by seconds.

Security and privacy are also affected because the public state and SSE endpoints disclose the complete HA state map rather than a Tapboard-specific projection.

## Evidence baseline

### Physical Tap 2 tests supplied by the user

The user's last physical pours were approximately 20:35 and 20:46 Eastern on 2026-07-31.

Recorder history around the first test showed:

- At approximately 20:34:32, Tap 1 dropped about 1.20 oz.
- At the same moment, Tap 2 dropped about 6.32 oz.
- Both drops exceeded the current 0.3 oz single-sample trigger.
- Tap 1's reading rebounded, demonstrating transient cross-coupling rather than a Tap 1 pour.

Recorder history around the second test showed:

- Tap 1 crossed the threshold at approximately 20:46:05.234.
- Tap 2 crossed at approximately 20:46:05.573, about 339 ms later.
- Subsequent Tap 1 impulses included drops around 2.16 oz and 1.71 oz.
- Tap 2's dominant impulses included drops around 1.14 oz and 2.52 oz.

The Tap 1 and Tap 2 entity mapping is correct in the current code. The incorrect Tap 1 indication is caused by Tap 1's own sensor transient plus the detector's threshold policy.

### False events after the last physical pour

The current container started after the user's last physical test. Timestamped logs then recorded:

- `2026-08-01T01:06:33Z`: Tap 1 pour start.
- `2026-08-01T01:06:38Z`: Tap 2 pour start.
- `2026-08-01T01:08:32Z`: both sessions finally completed.
- `2026-08-01T03:07:33Z`: another Tap 2 start, completed as 0.9 oz.
- `2026-08-01T05:16:31Z`: another Tap 2 start, completed roughly 22.6 seconds later and logged as 2.1 oz.

Because no physical pours occurred after approximately 20:46 Eastern, these later sessions are false positives or noise-induced sessions.

### Event-stream measurements

- HA snapshot contained approximately 1,273 entities.
- One `/api/state` response measured 265,257 bytes.
- The two fast sensors alone publish about ten combined updates per second.
- That implies at least roughly 2.65 MB/sec per browser before other HA entities are counted.
- A container resource snapshot showed approximately 132 GB transmitted.
- The browser calls `renderApp()` for every `state_changed` event.

### Dependency status

- Deployed `npm audit --omit=dev` result: zero known vulnerabilities.
- Installed direct versions from the lockfile included `bcryptjs` 2.4.3, `better-sqlite3` 11.10.0, `dotenv` 16.6.1, and `ws` 8.21.1.
- Several major-version upgrades are available, but dependency upgrades are not the immediate security priority.

## Prioritized findings

### P0 — Pour sessions can remain active indefinitely

**Location:** `src/haClient.js`, active-pour timer handling.

Every accepted sensor update clears and recreates the settle timer. Since the fast sensor updates every 0.2 seconds, the timer normally cannot expire.

**Required direction:** Track the timestamp of the last meaningful downward-flow signal. Do not reset the quiet-period timer for flat, rising, or insignificant readings.

### P0 — Tap 1 cross-triggers during Tap 2 operation

**Location:** `src/haClient.js`, pour-start decision.

A single 0.3 oz drop starts a pour. Tap 1 experienced transient drops well above that threshold during both Tap 2 tests.

**Required direction:** Use a short robust sample window, sustained movement, and cross-tap arbitration. If simultaneous physical pours are not a requirement, enforce one active tap and select the tap with dominant sustained loss.

### P0 — Pour volume is inflated by noise

**Location:** `src/haClient.js`, `totalPoured` accumulation.

Every negative fluctuation is added while positive rebounds are ignored. Long sessions therefore convert ordinary jitter into fictitious poured volume.

**Required direction:** Calculate completed volume from a robust start baseline minus a robust settled end baseline.

### P0 — Public endpoints disclose all Home Assistant states

**Locations:** `src/haClient.js`, `src/server.js`.

`getFormattedState()` exposes every hydrated HA entity through public `/api/state`, initial SSE snapshots, and state-change messages. Tapboard may therefore reveal presence and other unrelated household states.

**Required direction:** Maintain an explicit Tapboard entity allowlist and expose only the fields needed by the UI.

### P0 — State-change payload and rendering volume are excessive

**Locations:** `src/haClient.js`, `src/server.js`, `public/app.js`.

Each state event includes a complete formatted HA state map, and the client fully traverses the active dashboard for each event.

**Required direction:** Send only changed Tapboard data, throttle display-only telemetry, coalesce browser renders, and handle SSE backpressure.

### P1 — Stored cross-site scripting paths

**Location:** `public/app.js`.

Beer names, styles, descriptions, batch fields, and catalog values are interpolated into `innerHTML`. Sources include HA, Brewfather, and stored overrides.

**Required direction:** Build content with DOM nodes and `textContent`, or use a narrowly configured sanitizer where HTML is intentionally supported.

### P1 — Unauthenticated simulation endpoint mutates data

**Location:** `src/server.js`, `/api/taps/:id/simulate-pour`.

The endpoint broadcasts events and inserts database records without authorization or tap-range validation.

**Required direction:** Remove it from production or require authorization and an explicit development-mode feature flag.

### P1 — Authentication and request hardening gaps

**Locations:** `src/server.js`, `src/db.js`.

- Default PIN is `0000`.
- Rate limiting is in memory and resets with the process.
- Sessions are stored as plaintext bearer tokens and are not revoked when the PIN changes.
- JSON request bodies have no size limit.
- CORS allows every origin.
- Internal error messages are returned to clients.
- Security headers are absent.

### P1 — Unit conversion uses value magnitude

**Location:** `src/haClient.js`.

Any value over 350 is treated as milliliters. A valid Tap 3 reading of 640 fl. oz. is therefore interpreted as approximately 21.6 oz.

**Required direction:** Convert using an explicit normalized unit map. Unknown or conflicting units must fail closed and log a diagnostic.

### P1 — Fast sensors are retained by HA recorder

**Location:** related HA `configuration.yaml` recorder exclusions.

The stable raw sensors are excluded, but the two 5 Hz fast sensors are not. With 365-day retention, this can create hundreds of millions of recorder rows.

**Required direction:** Exclude fast sensors from recorder while retaining their live state events. If history is needed, record a separate low-rate diagnostic sensor.

### P1 — Reverse-proxy and trusted-network configuration is broad

**Location:** related HA `configuration.yaml`.

- `trusted_proxies` includes `172.0.0.0/8` rather than the exact proxy address or narrowly scoped subnet.
- One trusted-network host can bypass login as a fixed HA user.

These settings should be reviewed against the actual network topology.

### P1 — Shell command filename is not contained

**Location:** related HA `configuration.yaml`, `write_tapboard_json` command.

The decoded `filename` is appended to a directory without rejecting `..`, absolute paths, or unexpected filenames.

**Required direction:** Resolve the target path, enforce directory containment, and preferably allowlist the few expected filenames.

### P2 — Forecast data and time handling are unreliable

**Locations:** `src/server.js`, `src/db.js`.

- SQLite `CURRENT_TIMESTAMP` strings are compared lexically against JavaScript ISO timestamps.
- `batch_id` is not written with physical pour logs.
- Forecasts can mix multiple kegs on the same tap.
- `active_days` is queried but unused.
- `pour_logs(tap_id, timestamp)` lacks a supporting index.

### P2 — Large changes can permanently stale a tracker

**Location:** `src/haClient.js`.

Changes over 30 oz are ignored without a confirmed-plateau rebaseline. A keg replacement or legitimate large correction can therefore leave every later reading more than 30 oz away from the stored baseline.

### P2 — HA WebSocket lifecycle needs hardening

**Location:** `src/haClient.js`.

- Pending requests are not rejected or cleared on disconnect.
- Hydration event buffering is unbounded.
- A failed sync has no explicit retry state.
- Authentication failure does not cleanly stop or retry.
- Reconnect logging shows repeated connection-state notifications.

### P2 — Container hardening and persistence

**Locations:** `Dockerfile`, `docker-compose.yml`.

- Runtime defaults to root.
- Port 3005 binds on all host interfaces.
- HA token is passed as a normal environment variable.
- Base image is a floating tag rather than a pinned digest.
- SQLite WAL files reside in a OneDrive-synchronized bind mount.

Prefer a non-root user, least-privilege container options, narrowly bound networking, secret-file injection, and a local Docker volume with separate backups.

### P2 — Schema and validation gaps

**Locations:** `src/db.js`, `src/server.js`.

- SQLite foreign keys are not enabled.
- Migrations suppress all exceptions.
- Enums, ranges, and string sizes are not validated consistently.
- End-batch and end-keg routes do not apply the same 1–6 tap validation as the update route.
- Expired admin sessions are never pruned.

### P3 — Documentation and implementation drift

- Architecture version: 3.7.2.
- Client comment: 3.8.2.
- Package and README: 3.2.0.
- Graphics and CSS carry additional versions.
- Architecture describes a 0.8 oz/3-second trigger and 5-second quiet period, while code uses a 0.3 oz single-sample trigger and 1.5-second timer.
- Architecture describes a JWT, while the server uses an opaque stored session token.
- `config/www/tapboard` contains a second, differing frontend implementation.

## Work batches

### Batch 1 — Pour detector correctness and deterministic tests

**Priority:** Highest

**Primary files:** `src/haClient.js`; new detector module and tests as justified by the approved plan.

**Goals:**

- Eliminate stuck sessions under continuous telemetry.
- Reject Tap 1 transients during Tap 2 pours.
- Reject idle noise and startup transients.
- Produce defensible poured-volume totals.
- Preserve sub-second or near-sub-second start feedback.
- Use declared units only.

**Design constraints:**

- Detection logic should be independently testable without a live HA connection or real-time waits.
- Use an injectable/fake clock or explicit sample timestamps.
- Start decisions should use a robust short window rather than one sample.
- Cross-tap arbitration must be explicit and documented.
- Quiet-period timing must be based on the last meaningful flow, not last telemetry.
- Completion volume must use robust start/end baselines.
- Persistent large plateaus need a safe rebaseline path.
- Do not change ESPHome or live HA configuration in this batch.

**Acceptance criteria:**

- [ ] Continuous flat 0.2-second samples allow an active session to finish after the configured quiet period.
- [ ] Positive rebounds and sub-threshold jitter do not extend a pour.
- [ ] Replaying representative 20:35 and 20:46 traces selects Tap 2 and does not emit a Tap 1 pour.
- [ ] Idle/startup traces from after 20:46 do not produce completed physical pours.
- [ ] Poured volume is based on net robust baseline loss and is not inflated by oscillation.
- [ ] Milliliters and fluid ounces are converted strictly from declared units.
- [ ] A legitimate stable large change can rebaseline without generating a pour.
- [ ] Tests cover restart/hydration, unavailable states, spikes, rebound, slow pours, and completion.
- [ ] Existing SSE event names and UI behavior remain compatible unless an approved plan explicitly changes them.
- [ ] Container or local test suite passes without requiring live HA mutation.

**Out of scope:** Full SSE redesign, frontend XSS remediation, recorder changes, and production deployment.

### Batch 2 — SSE performance, data minimization, and UI latency

**Priority:** Highest, after or coordinated carefully with Batch 1

**Primary files:** `src/haClient.js`, `src/server.js`, `public/app.js`.

**Acceptance criteria:**

- [ ] Public endpoints expose only Tapboard-required entities and fields.
- [ ] Ordinary `state_changed` payloads contain no full HA snapshot.
- [ ] Pour events are not queued behind display telemetry.
- [ ] Display updates are throttled/coalesced without slowing backend detection.
- [ ] Only affected cards are updated for telemetry changes.
- [ ] SSE backpressure and disconnected clients are handled.
- [ ] A lightweight health endpoint replaces `/api/state` in the healthcheck.
- [ ] Payload size and event-rate measurements before and after are recorded here.

### Batch 3 — Web/API security hardening

**Priority:** High

**Primary files:** `src/server.js`, `src/db.js`, `public/app.js`, deployment configuration.

**Acceptance criteria:**

- [ ] Untrusted content is not inserted through unsafe `innerHTML` paths.
- [ ] Simulation is removed from production or authenticated and feature-flagged.
- [ ] JSON body sizes and content types are enforced.
- [ ] CORS is same-origin or explicitly allowlisted.
- [ ] Security headers and reverse-proxy HTTPS expectations are documented.
- [ ] Default PIN requires deliberate initialization/change.
- [ ] PIN change revokes existing sessions; expired sessions are pruned.
- [ ] Route inputs use shared validation and safe public error messages.
- [ ] Static asset path containment uses resolved path boundaries.

### Batch 4 — ESPHome and Home Assistant telemetry hygiene

**Priority:** High

**Primary systems:** ESPHome scale YAML and HA recorder configuration.

**Acceptance criteria:**

- [ ] Fast sensors remain suitable for live detection.
- [ ] A small median or comparable robust fast filter is evaluated against saved traces.
- [ ] Fast sensors are excluded from recorder, or an explicit retention strategy is documented.
- [ ] A low-rate diagnostic/history sensor exists if long-term traceability is required.
- [ ] Mechanical isolation, beer-line strain relief, grounding, power decoupling, and HX711 rate are checked and documented.
- [ ] HA configuration is backed up and validated before any reload/restart.

### Batch 5 — Database, forecast, WebSocket, and deployment reliability

**Priority:** Medium

**Primary files:** `src/db.js`, `src/server.js`, `src/haClient.js`, `Dockerfile`, `docker-compose.yml`.

**Acceptance criteria:**

- [ ] Forecast queries use one normalized timestamp representation.
- [ ] Physical pour logs capture the active batch/keg identity.
- [ ] Forecasts do not mix successive kegs unless explicitly intended.
- [ ] Appropriate database indexes and foreign-key enforcement are present.
- [ ] Migrations distinguish expected duplicate-column cases from real failures.
- [ ] WebSocket disconnect rejects pending requests and bounds queues.
- [ ] Runtime uses a non-root user and least-privilege container settings.
- [ ] Database persistence is moved off OneDrive or the risk is explicitly accepted.
- [ ] Backup and restore procedures are tested.

### Batch 6 — Test infrastructure, documentation, dependency maintenance, and cleanup

**Priority:** Medium/low

**Primary files:** project-wide.

**Acceptance criteria:**

- [ ] A standard test and lint command exists in `package.json`.
- [ ] Architecture, README, package, client, CSS, and graphics versions agree.
- [ ] Architecture accurately describes the implemented detector and authentication model.
- [ ] The legacy `config/www/tapboard` implementation is removed, archived, or clearly designated.
- [ ] Ad-hoc database scripts are documented or replaced by supported commands.
- [ ] Major dependency upgrades are tested individually.
- [ ] Automated dependency monitoring is configured if desired.

2. Batch 2 — event delivery, privacy, and UI latency.
3. Batch 3 — web/API hardening.
