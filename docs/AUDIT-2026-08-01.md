## Executive summary

Tapboard's observed pour behavior has four interacting causes:

1. **Cross-tap sensor movement:** Operating Tap 2 produces a large transient drop on Tap 1's fast scale sensor. This is real input data, not just a UI card-selection bug.
2. **Over-sensitive start detection:** One sample dropping by 0.3 oz starts a pour, so physical coupling and ordinary scale impulses can trigger false sessions.
3. **Broken completion timing:** Every 0.2-second update restarts the settle timer, including flat and rising readings. A pour normally ends only when telemetry happens to pause.
4. **SSE overload:** Every HA state change serializes all HA entities and sends them to every browser. This produces a large backlog and can delay visible pour events by seconds.

Security and privacy are also affected because the public state and SSE endpoints disclose the complete HA state map rather than a Tapboard-specific projection.

## Prioritized findings

### P0 — Pour sessions can remain active indefinitely

**Location:** `src/haClient.js`, active-pour timer handling.

Every accepted sensor update clears and recreates the settle timer. Since the fast sensor updates every 0.2 seconds, the timer normally cannot expire.

**Required direction:** Track the timestamp of the last meaningful downward-flow signal. Do not reset the quiet-period timer for flat, rising, or insignificant readings.

### P0 — Tap 1 cross-triggers during Tap 2 operation

**Location:** `src/haClient.js`, pour-start decision.

A single 0.3 oz drop starts a pour. Tap 1 experienced transient drops well above that threshold during both Tap 2 tests.

**Required direction:** Use a short robust sample window, sustained movement, and cross-tap arbitration. If simultaneous physical pours are not a requirement, enforce one active tap and select the tap with dominant sustained loss.

### P0 — Pour volume is inflated by noise

**Location:** `src/haClient.js`, `totalPoured` accumulation.

Every negative fluctuation is added while positive rebounds are ignored. Long sessions therefore convert ordinary jitter into fictitious poured volume.

**Required direction:** Calculate completed volume from a robust start baseline minus a robust settled end baseline.

### P0 — Public endpoints disclose all Home Assistant states

**Locations:** `src/haClient.js`, `src/server.js`.

`getFormattedState()` exposes every hydrated HA entity through public `/api/state`, initial SSE snapshots, and state-change messages. Tapboard may therefore reveal presence and other unrelated household states.

**Required direction:** Maintain an explicit Tapboard entity allowlist and expose only the fields needed by the UI.

### P0 — State-change payload and rendering volume are excessive

**Locations:** `src/haClient.js`, `src/server.js`, `public/app.js`.

Each state event includes a complete formatted HA state map, and the client fully traverses the active dashboard for each event.

**Required direction:** Send only changed Tapboard data, throttle display-only telemetry, coalesce browser renders, and handle SSE backpressure.

### P1 — Stored cross-site scripting paths

**Location:** `public/app.js`.

Beer names, styles, descriptions, batch fields, and catalog values are interpolated into `innerHTML`. Sources include HA, Brewfather, and stored overrides.

**Required direction:** Build content with DOM nodes and `textContent`, or use a narrowly configured sanitizer where HTML is intentionally supported.

### P1 — Unauthenticated simulation endpoint mutates data

**Location:** `src/server.js`, `/api/taps/:id/simulate-pour`.

The endpoint broadcasts events and inserts database records without authorization or tap-range validation.

**Required direction:** Remove it from production or require authorization and an explicit development-mode feature flag.

### P1 — Authentication and request hardening gaps

**Locations:** `src/server.js`, `src/db.js`.

- Default PIN is `0000`.
- Rate limiting is in memory and resets with the process.
- Sessions are stored as plaintext bearer tokens and are not revoked when the PIN changes.
- JSON request bodies have no size limit.
- CORS allows every origin.
- Internal error messages are returned to clients.
- Security headers are absent.

### P1 — Unit conversion uses value magnitude

**Location:** `src/haClient.js`.

Any value over 350 is treated as milliliters. A valid Tap 3 reading of 640 fl. oz. is therefore interpreted as approximately 21.6 oz.

**Required direction:** Convert using an explicit normalized unit map. Unknown or conflicting units must fail closed and log a diagnostic.

### P1 — Fast sensors are retained by HA recorder

**Location:** related HA `configuration.yaml` recorder exclusions.

The stable raw sensors are excluded, but the two 5 Hz fast sensors are not. With 365-day retention, this can create hundreds of millions of recorder rows.

**Required direction:** Exclude fast sensors from recorder while retaining their live state events. If history is needed, record a separate low-rate diagnostic sensor.

### P1 — Reverse-proxy and trusted-network configuration is broad

**Location:** related HA `configuration.yaml`.

- `trusted_proxies` includes `172.0.0.0/8` rather than the exact proxy address or narrowly scoped subnet.
- One trusted-network host can bypass login as a fixed HA user.

These settings should be reviewed against the actual network topology.

### P1 — Shell command filename is not contained

**Location:** related HA `configuration.yaml`, `write_tapboard_json` command.

The decoded `filename` is appended to a directory without rejecting `..`, absolute paths, or unexpected filenames.

**Required direction:** Resolve the target path, enforce directory containment, and preferably allowlist the few expected filenames.

### P2 — Forecast data and time handling are unreliable

**Locations:** `src/server.js`, `src/db.js`.

- SQLite `CURRENT_TIMESTAMP` strings are compared lexically against JavaScript ISO timestamps.
- `batch_id` is not written with physical pour logs.
- Forecasts can mix multiple kegs on the same tap.
- `active_days` is queried but unused.
- `pour_logs(tap_id, timestamp)` lacks a supporting index.

### P2 — Large changes can permanently stale a tracker

**Location:** `src/haClient.js`.

Changes over 30 oz are ignored without a confirmed-plateau rebaseline. A keg replacement or legitimate large correction can therefore leave every later reading more than 30 oz away from the stored baseline.

### P2 — HA WebSocket lifecycle needs hardening

**Location:** `src/haClient.js`.

- Pending requests are not rejected or cleared on disconnect.
- Hydration event buffering is unbounded.
- A failed sync has no explicit retry state.
- Authentication failure does not cleanly stop or retry.
- Reconnect logging shows repeated connection-state notifications.

### P2 — Container hardening and persistence

**Locations:** `Dockerfile`, `docker-compose.yml`.

- Runtime defaults to root.
- Port 3005 binds on all host interfaces.
- HA token is passed as a normal environment variable.
- Base image is a floating tag rather than a pinned digest.
- SQLite WAL files reside in a OneDrive-synchronized bind mount.

Prefer a non-root user, least-privilege container options, narrowly bound networking, secret-file injection, and a local Docker volume with separate backups.

### P2 — Schema and validation gaps

**Locations:** `src/db.js`, `src/server.js`.

- SQLite foreign keys are not enabled.
- Migrations suppress all exceptions.
- Enums, ranges, and string sizes are not validated consistently.
- End-batch and end-keg routes do not apply the same 1–6 tap validation as the update route.
- Expired admin sessions are never pruned.

### P3 — Documentation and implementation drift

- Architecture version: 3.7.2.
- Client comment: 3.8.2.
- Package and README: 3.2.0.
- Graphics and CSS carry additional versions.
- Architecture describes a 0.8 oz/3-second trigger and 5-second quiet period, while code uses a 0.3 oz single-sample trigger and 1.5-second timer.
- Architecture describes a JWT, while the server uses an opaque stored session token.
- `config/www/tapboard` contains a second, differing frontend implementation.

## Work batches

### Batch 1 — Pour detector correctness and deterministic tests

**Priority:** Highest

**Primary files:** `src/haClient.js`; new detector module and tests as justified by the approved plan.

**Goals:**

- Eliminate stuck sessions under continuous telemetry.
- Reject Tap 1 transients during Tap 2 pours.
- Reject idle noise and startup transients.
- Produce defensible poured-volume totals.
- Preserve sub-second or near-sub-second start feedback.
- Use declared units only.

**Design constraints:**

- Detection logic should be independently testable without a live HA connection or real-time waits.
- Use an injectable/fake clock or explicit sample timestamps.
- Start decisions should use a robust short window rather than one sample.
- Cross-tap arbitration must be explicit and documented.
- Quiet-period timing must be based on the last meaningful flow, not last telemetry.
- Completion volume must use robust start/end baselines.
- Persistent large plateaus need a safe rebaseline path.
- Do not change ESPHome or live HA configuration in this batch.

**Acceptance criteria:**

- [x] Continuous flat 0.2-second samples allow an active session to finish after the configured quiet period.
- [x] Positive rebounds and sub-threshold jitter do not extend a pour.
- [x] Replaying representative 20:35 and 20:46 traces selects Tap 2 and does not emit a Tap 1 pour.
- [x] Idle/startup traces from after 20:46 do not produce completed physical pours.
- [x] Poured volume is based on net robust baseline loss and is not inflated by oscillation.
- [x] Milliliters and fluid ounces are converted strictly from declared units.
- [x] A legitimate stable large change can rebaseline without generating a pour.
- [x] Tests cover restart/hydration, unavailable states, spikes, rebound, slow pours, and completion.
- [x] Existing SSE event names and UI behavior remain compatible unless an approved plan explicitly changes them.
- [x] Container or local test suite passes without requiring live HA mutation.

**Verified 2026-08-01:** `docker run --rm ... node:22-alpine npm test` passed all 11 deterministic tests. Representative audit-derived traces selected and completed Tap 2 only; continuous 0.2-second flat samples completed on the meaningful-flow quiet deadline; oscillation produced robust net loss; declared-unit, unavailable, stale, spike, slow-pour, large-plateau, cooldown, and 15-second timeout cases passed. Node 22 syntax checks passed for every changed JavaScript file, and `git diff --check` passed. No live HA state, container, or ESPHome configuration was mutated.

**Out of scope:** Full SSE redesign, frontend XSS remediation, recorder changes, and production deployment.

- [x] A small median or comparable robust fast filter is evaluated against saved traces.

2026-08-01 — Batch 1 — Deterministic single-active-tap detector

Context: Tap 1 transients accompanied Tap 2 pours, per-sample timers prevented completion, negative jitter inflated totals, and value magnitude incorrectly implied units.

Decision: Use a pure timestamp-driven detector with a robust 0.8 oz candidate window, 400 ms dominant-loss arbitration, one active tap, 0.2 oz meaningful-flow lows, a five-second quiet period, robust baseline-to-settled-end volume, declared-unit conversion, stable large-change rebaselining, and a 15-second safety cancellation. Add an additive `pour_cancel` event so canceled sessions always stop the UI animation without a completion toast.

Alternatives considered: Parallel pours, single-sample starts, accumulated negative deltas, magnitude-based unit inference, and representing cancellations as zero-volume completions.

Consequences: Normal start feedback is approximately 0.8 seconds. Ambiguous simultaneous movement is suppressed. A continuing session is canceled after 15 seconds, and post-session detection waits for cooldown plus a settled rebaseline. Existing `pour_start` and `pour_complete` payloads remain compatible.

Verification: Eleven deterministic Node tests and syntax/diff checks passed in a one-off Node 22 container. No production deployment or live HA mutation was performed.

2026-08-01 — Batch 2 — Semantic public projection and bounded SSE delivery

Context: Public snapshots exposed approximately 1,273 complete HA entities, ordinary state events repeated that snapshot at high frequency, browsers rendered the full dashboard per event, and slow SSE consumers had no bounded backpressure policy.

Decision: Keep the complete HA map backend-only. Project exact Tapboard entities and allowlisted fields into a versioned `tapStates` schema, coalesce display deltas globally over 250 ms, preserve synchronous detector ingestion and immediate pour events, update only dirty cards in one animation frame, and use an SSE hub with heartbeat, lifecycle cleanup, and disconnect-on-sustained-backpressure behavior. Replace the Docker `/api/state` healthcheck with `/healthz`.

Alternatives considered: Publishing an allowlisted entity-name map, throttling the detector itself, retaining full snapshots in ordinary events, per-client unbounded queues, replay buffers, and rebuilding all cards for each delta.

Consequences: `/api/state` and snapshot consumers must migrate from `haStates` to schema-v2 `tapStates`. Healthy clients receive compact deltas at no more than four display events per second; detector samples and pour events remain immediate. Slow clients reconnect to a fresh snapshot instead of accumulating an application queue. Settings changes remain low-frequency full schema-v2 snapshots.

Verification: Thirty-two Node 22 tests passed. The seeded full snapshot was 3,478 bytes, a typical delta was 79 bytes, a 1,273-entity fixture projected from 398,499 to 685 bytes, and 10 Hz display input coalesced to four events per second. Privacy, priority ordering, 100/100 fast-sample ingestion, affected-card rendering, SVG preservation, real HTTP SSE lifecycle, health output, and bounded backpressure tests passed. Node syntax and diff checks passed. No production deployment or live HA mutation was performed.

2026-08-01 — Batch 3 — Fail-closed browser and API boundary

Context: Stored HA/Brewfather/catalog values reached HTML-string sinks; simulation was unauthenticated; request bodies, origins, route values, sessions, static paths, and public errors lacked consistent hardening; and the legacy `0000` hash required a migration that would not lock out an existing installation unexpectedly.

Decision: Build all untrusted UI content with DOM nodes and text properties while retaining only the normalized application-generated SVG string path. Remove simulation completely. Enforce a 16 KiB JSON ceiling, exact JSON media type, strict same-origin or `TAPBOARD_PUBLIC_ORIGIN`, centralized CSP and security headers, shared closed-schema validation, stable public errors, and real-path static containment. Store only SHA-256 bearer-token digests, retain 24-hour expiry, prune expired/legacy sessions, and revoke every session transactionally on PIN change. Add explicit `admin_pin_initialized` state: new and legacy-default databases remain viewable but admin-locked until a non-default one-time environment PIN is supplied; legacy non-default hashes migrate unchanged. Keep HSTS and HTTPS redirects at the reverse proxy.

Alternatives considered: Sanitizing user-authored HTML, retaining a development simulation route, wildcard CORS, shipping a default PIN, silently choosing a first-run PIN, storing bearer tokens directly, allowing unknown fields, emitting HSTS over direct HTTP, and permitting iframe embedding.

Consequences: Existing sessions are intentionally invalidated on upgrade. Existing API clients must send accepted JSON types and fields. Reverse proxies must configure the exact public origin. Tapboard cannot be framed. A legacy-default installation requires the documented backup and one-time private PIN initialization before admin mutations work. The Docker build context now excludes `.env` and live data.

Verification: Twenty-one focused security tests and all 53 repository tests passed; all 32 prior tests remained green. Node syntax and diff checks passed. The production image built successfully and reported zero production dependency vulnerabilities. A read-only security review found no critical or high-severity issue; its method handling, snapshot-error, abort, proxy-OPTIONS, symlink, and static-method coverage findings were resolved before the final suite. After a separately authorized online backup and migration, the port-3005 container was healthy on Batch 3, the database remained integral, prior sessions were revoked, the operator authenticated with the initialized PIN, the temporary plaintext environment value was removed, and a second recreation preserved only a non-expired hashed session. Home Assistant and ESPHome configuration were not changed.

2026-08-01 — Batch 4 — Recorder-only fast telemetry hygiene

Context: Tapboard requires both approximately 5 Hz scale streams for prompt backend detection, but Home Assistant was retaining roughly 33,500 fast rows per hour with 365-day recorder retention. The already-recorded stable fl-oz sensors provided sufficient long-term operational traceability.

Decision: Keep both fast entities live and unchanged, exclude only their exact entity IDs from recorder, purge only their raw history and long-term statistics, and continue recording `sensor.tap_1_fl_oz` and `sensor.tap_2_fl_oz`. Do not add another diagnostic sensor. Defer ESPHome filtering and physical changes; revisit the trace-validated three-sample median only if cross-tap behavior remains observable during real pours.

Alternatives considered: Recording the fast streams with shorter retention, adding a new low-rate diagnostic sensor, deploying the three-sample median immediately, using a five-sample median, changing detector thresholds, and performing firmware or mechanical work in this phase.

Consequences: Tapboard keeps current live detector inputs and stable historical weight visibility without ongoing 5 Hz recorder growth. Historical fast raw states and statistics were intentionally deleted for exactly the two approved sensors. Firmware and calibration risk were avoided, but the mechanical checklist and real-pour confirmation remain open.

Verification: A fresh database-capable backup and byte-identical configuration rollback were secured first. The reviewed live diff added exactly two recorder exclusions, Home Assistant configuration checks passed, the approved restart completed, live fast timestamps advanced after recording stopped, stable history continued, the exact purge verified at zero raw and statistic rows, all 60 tests passed, and Tapboard health returned HTTP 200.
